# FaceBlock — Implementation Plan

## 1. Goal

Build a lightweight browser extension that automatically hides faces belonging to people the user has chosen to block.

The extension should work even when the person appears in:

- screenshots
- reposted photos
- memes
- avatars
- collages
- thumbnails
- embedded media
- videos

The system must operate locally in the browser wherever practical.

The core product principle is:

> Block the person, not just the account.

The first target is X/Twitter in Chromium-based browsers.

---

## 2. Core Requirements

### Functional requirements

The extension must:

1. Detect faces in images visible on X.
2. Compute an identity embedding for each detected face.
3. Compare the embedding against locally stored blocked-person embeddings.
4. Draw an opaque black box over matching faces.
5. Avoid uploading browsing activity or face embeddings to a server.
6. Allow users to add and remove blocked identities.
7. Allow multiple reference embeddings per blocked identity.
8. Cache already-processed media.
9. Avoid repeatedly running inference on off-screen content.
10. Fail safely when confidence is uncertain.

### Non-goals for v0

Do not implement initially:

- custom model training
- fine-tuning per blocked person
- cloud inference
- large vector databases
- full-video frame-by-frame inference
- cross-browser support beyond Chromium
- mobile browser support
- automatic public-figure enrollment

These can be added after the core matching pipeline is validated.

# 4. Computer Vision Stack

## Face detector

Preferred order for prototyping:

1. FaceX lightweight detector
2. MediaPipe Face Detector
3. lightweight SCRFD ONNX model

The detector should provide:

- bounding box
- face confidence
- facial landmarks if available

The detector does not need generic object-detection capabilities.

Avoid full YOLO unless testing shows a clear practical advantage.

---

## Face embedding model

Use a pretrained lightweight face-recognition embedding model.

Preferred:

- MobileFaceNet
- ArcFace-compatible embedding space

Target characteristics:

- input: approximately `112 x 112 RGB`
- output: `128–512` floating-point embedding
- model size: ideally `<10 MB`
- ONNX-compatible

No person-specific fine-tuning is required.

---

## Runtime

Use:

```text
ONNX Runtime Web
├── WebGPU
└── WASM SIMD fallback
```

WebGPU should be attempted first.

WASM must remain available so the extension works on systems without reliable WebGPU support.

# 7. Face Alignment

Before embedding:

1. detect face
2. obtain landmarks when possible
3. align eyes/nose to canonical orientation
4. crop
5. resize to model input size
6. normalize pixel values exactly as required by the model

Implement preprocessing as its own module.

```ts
alignFace(
  image: ImageData,
  detection: FaceDetection
): Tensor
```

Do not duplicate preprocessing logic between enrollment and live inference.

Enrollment and live matching must use the exact same preprocessing pipeline.

---

# 8. Identity Representation

Each blocked person should contain multiple embeddings.

Example:

```ts
interface BlockedIdentity {
  id: string;
  displayName?: string;
  embeddings: Float32Array[];
  prototypes?: Float32Array[];
  threshold: number;
  createdAt: number;
}
```

Display names are optional.

The recognition engine should not require the identity to have a human-readable name.

Example:

```text
identity_f7a82c1d
```

is sufficient.

---

# 9. Matching

Normalize embeddings with L2 normalization.

Use cosine similarity:

```text
similarity(a, b) = dot(a, b)
```

when both vectors are normalized.

Initial matching:

```ts
score = max(
  cosine(queryEmbedding, referenceEmbedding)
  for referenceEmbedding in identity.embeddings
)
```

Censor only when:

```text
score >= identity.threshold
```

Use a conservative default threshold.

Do not try to maximize recall at the expense of false positives.

For this product:

```text
false negative < false positive
```

in terms of UX cost.

It is better to occasionally miss the blocked person than censor an unrelated person.

---

# 10. Prototype-Based Matching

After basic matching works, improve each identity using clustering.

For each identity:

```text
raw reference embeddings
 ↓
clustering
 ↓
remove outliers
 ↓
retain representative prototypes
```

Possible methods:

- DBSCAN
- HDBSCAN
- k-medoids
- centroid + nearest exemplars

Prefer representative exemplars over relying exclusively on a single centroid.

Example:

```text
Person A
├── frontal prototype
├── profile-left prototype
├── profile-right prototype
├── glasses prototype
└── older/newer appearance prototype
```

# 11. Enrollment — Phase 1

The initial enrollment system should be manual.

Workflow:

```text
user opens extension
 ↓
Add blocked person
 ↓
select/upload reference images
 ↓
detect faces
 ↓
user confirms correct face
 ↓
generate embeddings
 ↓
store locally
```

Require at least:

```text
3 reference images
```

Recommend:

```text
5–15 images
```

Do not store reference photographs after successful enrollment unless the user explicitly chooses to.

Store:

- embeddings
- optional small metadata
- thresholds

# 12. Enrollment — Phase 2: Browser-Assisted Discovery

After manual enrollment works, implement automatic candidate collection.

Desired workflow:

```text
"Block [person]"
 ↓
search/browser agent
 ↓
retrieve candidate images
 ↓
collect context around each image
 ↓
candidate scoring
 ↓
face detection
 ↓
embedding clustering
 ↓
outlier rejection
 ↓
present enrollment preview
 ↓
user confirms
 ↓
store prototypes locally
```

Use a browser/search agent only to discover candidate references.

Do not use an LLM/Jev-style model as the face-recognition engine.

Its role is contextual validation.

Possible questions for the reasoning layer:

```text
Is this image likely to depict the requested person?

Does the caption identify the person?

Is the requested person probably the central subject?

Is this likely a duplicate image?

Does the page context contradict the candidate identity?
```

---

# 13. Automated Identity Construction

For automatic enrollment:

1. collect approximately 20–50 candidate images
2. run face detection
3. discard images with no face
4. initially prefer images with exactly one prominent face
5. embed all detected candidates
6. cluster embeddings
7. identify the dominant internally consistent cluster
8. reject isolated/outlier embeddings
9. retain approximately 5–10 representative prototypes
10. show the resulting face set to the user for confirmation

Never silently assume the largest cluster is correct without user confirmation in the first implementation.

---

# 14. Extension Media Privacy

Local-first privacy is mandatory.

The extension should not transmit:

- X timeline images
- face crops
- browsing history
- blocked-person embeddings
- blocked-person names
- matching results

unless a future feature explicitly requires it and the user opts in.

Document this in the UI.

Suggested product language:

> Face matching happens on your device.

---

# 15. Avoiding Visible Flashing

Do not render an uncensored blocked face and hide it afterward.

Potential approach:

```text
media enters viewport
 ↓
temporarily conceal or blur media
 ↓
run inference
 ↓
no blocked face?
 └── reveal original

blocked face?
 └── reveal with censor overlay
```

However, avoid making the whole feed feel sluggish.

Implement a configurable strategy:

### Mode A — Fast

Reveal immediately and apply masks as soon as inference finishes.

### Mode B — Strict

Temporarily conceal new media until classification completes.

Default to Fast during early development.

Measure inference latency before deciding the production default.

---

# 16. Overlay Renderer

Implement censorship independently of the CV engine.

Input:

```ts
interface CensorRegion {
  x: number;
  y: number;
  width: number;
  height: number;
  confidence: number;
  identityId: string;
}
```

Render an absolutely positioned DOM element over the image.

Default:

```text
solid black rectangle
```

Expand face boxes slightly:

```text
x -= width * marginX
y -= height * marginY
width *= scaleX
height *= scaleY
```

This prevents hair/ears/face edges from remaining obviously identifiable.

Support later:

- blur
- pixelation
- custom solid colors
- replacement images
- novelty modes

Keep black box as the v0 default.

---

# 17. Coordinate Handling

X may:

- resize images
- crop them
- use `object-fit`
- lazy-load them
- replace image elements
- resize posts dynamically

Therefore:

1. perform detection in source-image coordinates
2. calculate displayed element dimensions
3. account for cropping/object-fit
4. map source coordinates to rendered coordinates
5. recompute overlays on resize

Use:

```text
ResizeObserver
```

to keep masks attached to the correct region.

---

# 18. Mutation / Visibility Strategy

Do not scan the entire DOM repeatedly.

Use:

```text
MutationObserver
 ↓
discover candidate media
 ↓
IntersectionObserver
 ↓
only process visible media
```

Maintain states:

```ts
enum ProcessingState {
  Unseen,
  Queued,
  Processing,
  Processed,
  Failed
}
```

---

# 19. Cache

Create a media-result cache.

Key candidate:

```text
hash(source URL + image dimensions)
```

or eventually:

```text
perceptual image hash
```

Cache:

- detected faces
- embeddings
- matching decisions

Avoid recomputing inference when:

- scrolling away and back
- X reuses an image
- the DOM is reconstructed
- the same avatar occurs repeatedly

Use an LRU policy if cache size becomes large.

---

# 20. Performance Strategy

The target should be ordinary laptops.

Avoid optimizing first for the M3 Max.

The M3 Max is development hardware, not the minimum target.

### Rules

- only inspect visible media
- batch face embedding inference where possible
- use WebGPU when available
- WASM SIMD fallback
- cache aggressively
- skip tiny media
- skip faces below minimum size
- avoid re-embedding identical faces
- limit concurrency

Possible queue:

```text
max detector jobs: 1–2
max embed jobs: 4–8
```

Tune experimentally.

---

# 21. Initial Performance Targets

For still images:

```text
P50 full image processing: <100 ms
P95 full image processing: <300 ms
```

These are aspirational development targets, not hard assumptions.

Measure separately:

- decode
- detection
- alignment
- embedding
- matching
- DOM overlay

Create performance telemetry locally during development.

---

# 22. Video — Later Phase

Do not run recognition at 30 or 60 FPS.

Pipeline:

```text
video
 ↓
sample key frame every ~300–500 ms
 ↓
face detection
 ↓
face embedding
 ↓
identity match
 ↓
track face between recognition frames
 ↓
periodic refresh
```

Possible trackers:

- simple IoU tracking
- Kalman filter
- lightweight optical flow
- browser-friendly box tracker

Recognition should occur only:

- when a new face appears
- when tracking confidence is lost
- periodically for correction

---

# 23. False-Positive Feedback

Add:

```text
Not this person
```

when the user interacts with a censor box.

Store that face embedding as a hard negative.

Schema:

```ts
interface HardNegative {
  identityId: string;
  embedding: Float32Array;
}
```

Later matching can penalize embeddings close to hard negatives.

Example:

```text
positive similarity = 0.71
negative similarity = 0.69

decision confidence becomes low
→ do not censor
```

---

# 24. Local Storage

Use IndexedDB for:

- identities
- embeddings

- settings
- media cache

Do not rely on `chrome.storage.sync` for large embedding data.

Use `chrome.storage.local` only for lightweight settings.

# 27. Evaluation Dataset

Build an internal development test set.

For each blocked identity:

```text
reference images: 5–15
positive test images: 25–100
negative images: 500+
```

Include:

- frontal
- side profile
- smiling
- neutral
- glasses
- hat
- facial hair
- poor lighting
- low resolution
- screenshot compression
- partial occlusion
- group images

Negative set should intentionally include:

- visually similar people
- same gender presentation
- similar hair
- similar age
- same ethnicity where appropriate
- celebrity lookalikes
- low-resolution faces

This matters more than easy random negatives.

# 29. Threshold Calibration

Do not hardcode a threshold copied from another benchmark.

Calibrate on the actual chosen model.

For each model:

1. collect positive pairs
2. collect hard-negative pairs
3. calculate cosine similarity distributions
4. choose a conservative operating threshold
5. validate on unseen identities

Potential future feature:

```text
Strict
Balanced
Aggressive
```

These modes should map to explicit calibrated thresholds.

- execute remotely hosted extension code
- expose face embeddings to page JavaScript

# 37. Definition of v0 Success

v0 is successful when:

1. User manually enrolls a person with 5–15 reference photos.
2. The extension stores only embeddings/prototypes.
3. User opens X.
4. Visible images are automatically scanned locally.
5. The blocked person is recognized across unrelated posts/screenshots.
6. A black rectangle is placed over their face.
7. Unrelated people are almost never censored.
8. Feed scrolling remains smooth.
9. Nothing needs to be uploaded to a FaceBlock server.
10. The system works on CPU/WASM if WebGPU is unavailable.

# 39. Guiding Principle

Keep the ML layer boring.

The competitive/product value is not inventing another face-recognition model.

The useful product is:

```text
small detector
+
small embedder
+
good reference curation
+
conservative matching
+
fast browser integration
+
strong privacy defaults
```

Do not fine-tune until benchmarking demonstrates that pretrained embeddings are insufficient.
